# Чек-листы, фото и отчёты — тестовая интеграция

Состояние: тестовая ветка; рабочее приложение не опубликовано. Клиенты, QR-коды,
штампы, подарки и меню не мигрируют. Код работы с лояльностью не изменён.

## Что изменено

- Админка: отдельные шаблоны открытия, дня и закрытия для точек 1 и 2;
  добавление, редактирование, архивирование/возврат пункта, обязательное фото.
- Сотрудник: общий фотоотчёт и фото по пунктам; съёмка или выбор из галереи;
  несколько накладных, фото отчёта по выручке и фото закрытой точки.
- IndexedDB: фото и очередь сохраняются до отправки. Никакие пароли не кладутся
  в очередь. Подтверждение Google обязательно; при сбое отчёт остаётся в очереди.
- Google Drive: файлы наследуют доступ закрытой папки, публичная ссылка не включается.
  В таблицу и Firebase записываются URL, а не base64-изображения.
- Apps Script: сервер проверяет сотрудника и кофейню, версию шаблона, суммы и фото;
  архивирует версии чек-листа; фиксирует снимок отчёта; повторный запрос с тем же ID
  не создаёт вторые строки/фотографии. Незавершённая отправка возобновляется.
- Существующие листы/столбцы сохраняются. Новые столбцы для фото, этапа и ID отчёта
  дописываются справа. Расходы зеркалируются в старую схему агрегатов.

## Проверка и подключение

10 октября 2026 выполнена живая проверка из аккаунта владельца: для каждой точки
созданы синтетические поставка, дневной чек-лист и закрытие смены. В Drive сохранены
фото накладной, чек-листа, закрытия и выручки. Все шесть отчётов получили `synced`;
каждый повторён с тем же ID. Это проверка серверной записи, а не мобильного интерфейса
или публичного endpoint. Предыдущий пробный запуск для точки 1 также остаётся в копии.

1. `node --test tests/operations.test.cjs` — тесты UI-разметки, очереди, ошибок,
   шаблонов, обязательных фото, изоляции сотрудников, идемпотентности и сумм.
   Это имитация сервисов, а не подтверждение живой интеграции.
2. В отдельном Apps Script выполните `runIntegrationSmokeTest`. Google потребует
   разрешения на таблицы, Drive и внешние запросы. Функция создаёт только синтетические
   тестовые поставку, чек-лист и закрытие смены для обеих точек в копии/тестовом пространстве,
   затем повторяет их с теми же ID для проверки дублей. Гостей она не читает/не меняет.
3. Проверьте строки и фото, повторную отправку и доступ к снимкам в Google Drive.
4. Добавьте в Script Properties `ADMIN_PASSWORD` (действующий пароль администратора,
   вводится владельцем без передачи в чат). Остальные свойства выставляет тест:
   `MODE=test`, `SPREADSHEET_ID`, `PHOTO_FOLDER_ID`.
5. После проверки создайте отдельное web app deployment от владельца. Доступ
   endpoint требует явного согласования; отчёты защищаются серверной проверкой
   сотрудника, а настройки — `ADMIN_PASSWORD`. Секреты и OAuth-токены в GitHub не добавлять.
6. В `operations-v3.js` укажите тестовый deployment в `REPORTS_WEBHOOK_URL`.
   Сейчас поле пустое: нельзя заявлять, что отчёты уже попадают в Google Таблицу.
7. Проверьте мобильную камеру, качество текста накладной, восстановление фото после
   перезапуска, медленную сеть, iframe-подтверждения на реальном GitHub Pages origin.

## Перед рабочим запуском

Нужны проверка живого endpoint, Firebase rules, доступов и качества снимков. В старом
приложении PIN администратора находится в клиентском HTML, а личные пароли сотрудников
используются существующей Firebase-схемой. Это не замена полноценной серверной авторизации.
Новые расширенные доступы и смена паролей не выполняются автоматически.

Переключение в production выполняется отдельно, только после успешной проверки и
согласования запуска: рабочий spreadsheet ID, закрытая рабочая папка, `MODE=production`,
`OPS_V3_TEST_MODE=false`, рабочий endpoint. `runIntegrationSmokeTest` всегда возвращает
настройки в тестовый режим: в рабочем проекте его не запускают. Тестовую и рабочую
интеграции держать отдельными проектами/deployment. Merge в main публикует GitHub Pages.
